# Performance review — 2026-11-17

Scope: read-only inspection of current native SDL implementation. No device timings were collected and no claim below establishes a measured Miyoo frame time. References identify inspected source lines; concurrent main.cpp edits may shift them. No gameplay or rendering code was changed.

## Confirmed work on the UI thread

1. **Redundant quadratic row scoring on every rendered frame.** `src/main.cpp:1974` calls `rowScore` (`1492–1496`), calculating power for each unit. The same row then calls `boardCardPower` for each visible card at `1988`. `src/game.cpp:69–84` calculates each nonhero power using three complete row scans (Bond, Morale, Horn). For N nonhero cards in one row, the row score plus its labels perform roughly 6*N*N row-element visits per frame, before ability/name lookup costs. This happens even when the game state has not changed. Existing `Player::score` already avoids recalculating the overall totals during rendering. **Small correction:** compute a render snapshot of six row totals and per-instance card powers when rule state changes (play/revive/leader/weather/round/load), and read it during drawing. As a first smaller step, compute each card power once per row draw and reuse the sum and labels; this halves this work without changing rules. Keep engine calculations authoritative and test weather, Bond, Morale, Horn, spy and hero parity.

2. **AI evaluation blocks the next frame.** `src/main.cpp:4426` calls `performAi`, and `1442` directly invokes `chooseAiAction` before rendering. `src/ai.cpp:531–534` copies the entire Game and executes a real simulated `playCard` for every card in hand; `539–542` also simulates the leader. Weight helpers additionally copy a whole Player just to score a row (`41–50`), and repeat row scans. This is concrete synchronous allocation and rules work, especially on crowded boards. Its actual duration remains unmeasured. **Small correction:** time AI separately first; eliminate the unrelated deck/hand/graveyard copying in `scoreRow` by constructing a minimal Player with only the required flags and row. Preserve all source AI weights/RNG. If still over budget, evaluate a state snapshot off the render thread (or incrementally between frames), and apply the action only if the game's generation/turn still matches. Do not simply lower AI thinking delay or weaken rules.

3. **First-use audio decoding blocks the UI.** `src/audio.cpp:143–145` calls `load` on demand; `36` decodes the entire SFX MP3, followed by conversion/copy. `playMusic:159–162` calls `loadMusic` synchronously. Its `98–112` loop decodes the complete music file before returning, retaining all converted PCM: chunked temporary buffers do not make decoding streaming or asynchronous. The main loop calls `playMusic` at `src/main.cpp:4427`; the matching-key guard avoids repeated decoding once loaded. Thus first menu/match music and previously unused effect can stop rendering. At requested 22050 Hz mono S16 (`audio.cpp:17–20`), one minute retains about 2.65 MB of PCM, and both tracks remain cached. **Small correction:** preload the chosen track and required SFX behind a visible loading screen with event pumping; preferably ship device-ready PCM or add a bounded streaming worker/ring buffer for music. Decoding must remain outside the audio callback; the present callback only mixes cached PCM. Preloading everything without checking RAM would trade stalls for memory pressure.

4. **First-use image decode/rescale also blocks the frame.** `src/main.cpp:551–588` does synchronous filesystem read, `stbi_load`, CPU rescaling and texture creation from draw calls. Current byte-budget/current-frame protection (`591–607`) fixes the former fixed-count cache thrash, and ordinary cache hits do not decode. It does not eliminate first-use cost when a new card, effect or opponent portrait enters. **Small correction:** pre-size the packaged handheld assets offline, preload the current match working set during loading (including effect art), then lazy-load only exceptional images. Log decode counts and elapsed decode time, not only cache size. Failed image paths are currently not negatively cached, so repeated references to missing artwork repeat filesystem/decode attempts; retain a failed-path set with explicit retry on asset-directory reset.

## Rendering and timing risks requiring measurement

5. The software path (`src/main.cpp:3208–3213`) composes every pixel, uploads the entire 640x480 canvas and presents every iteration. Text (`127–136`) emits one SDL rectangle per lit glyph pixel; miniature row symbols (`1531–1534`) do the same. These are confirmed operations; their share of frame time is unknown. Cache immutable pixel icon masks/glyph atlas as textures, and cache static background composition before considering a complex dirty-rectangle renderer. Preserve native-resolution sharpness. Drawing the full board has materially more work than drawing card thumbnails alone.

6. The accelerated presentation renderer requests VSYNC (`3174`), but every iteration also sleeps a fixed 8 ms after present (`4433`). This is not an elapsed-time frame limiter and adds latency even if present already waited; missing a refresh deadline can produce uneven cadence. The exact SDL driver behavior on the device must be measured. Replace with a deadline-based cap for non-VSYNC fallback and avoid unconditional extra sleep after an actually blocking VSYNC present. Record render, present and sleep separately before choosing a rate.

7. **Intentional animation lock is distinct from frozen rendering.** Constants `205–208` specify 1000 ms preview, 499 ms flight, 1000 ms row-audio wait and 1650 ms ability effect. `434–453` extends input lock through flights, ability completion plus 600 ms, and scheduled sounds; `458–467` adds placement waits. A source-faithful action may therefore intentionally reject gameplay input for seconds while animation continues. Do not remove those timings merely to improve a frame-time measurement. Instrument lock deadline/reason alongside frame duration; permit non-mutating inspection/navigation where safe, and visibly communicate waiting. A long lock with smooth frames and a stalled frame need separate fixes.

8. `updateRowLayouts` (`519–533`) checks six row sizes each frame, rebuilding geometry only when counts change. This is bounded and not a convincing crowded-board hotspot. `playMusic`'s matching-key guard also makes its normal per-frame call cheap. Neither should be singled out as the cause without timing evidence.

## Verification gap and next acceptance run

The existing `--crowded-render-test` (`src/main.cpp:3259–3282`) draws 72 unique card miniatures for 120 frames. It checks zero repeat decodes, but **does not call drawMatch**, row scoring, row rearrangement, weather/effect animations, notifications, input, live AI or background audio. Its success criterion has no frame-time threshold. It usefully proves texture-cache stability for that fixture, not full-match playability.

Add a bounded full-loop benchmark with legal dense decks/boards, warm and cold assets, weather plus Bond/Morale/Horn, several simultaneous triggered flights, AI with many legal targets, and both music transitions. Record frame p50/p95/p99/max and counts over 33/50/100 ms, with separate update/AI/audio/decode/draw/present timings, current lock state, texture resident bytes and peak process memory. First-frame loading must be reported separately rather than excluded silently. Run the production software-composition path on the actual Miyoo, compare sparse and crowded scenes, and verify controls during animation. Desktop timings alone cannot certify device performance. Keep source-rule and animation-parity tests alongside the benchmark so optimization cannot silently simplify gameplay.

Recommended order: add timing visibility; remove duplicate render power work; avoid first-use decode during matches; reduce AI copying; then use device data to justify glyph/static-layer caching or scheduling changes. No background tasks or hardware runs were started during this audit.

## Follow-up: safe background AI contract

Inspection of `chooseAiAction` and its helpers found only `rngState` mutations to the supplied Game, via `roll` (`src/ai.cpp:32–35`). Candidate `playCard`/leader execution uses copied `preview`/`after` states. `performAiMulligan` is a different API and does mutate real decks; it must not use a result contract restricted to action plus RNG. Catalog generation (`tools/generate_catalog.py:117–120`) emits function-local static const vectors. Reads after initialization are safe; prewarm the catalog on main before launching work and never expose App, SDL, audio, or pointers into live Game to the worker.

Worker receives an owned Game snapshot and returns value-only `{action, rngBefore, rngAfter, generation, player, phase}`. Main accepts it only for the same generation, player, phase and starting RNG; then installs `rngAfter` exactly once and executes the already chosen action. Do not call `chooseAiAction` again on acceptance. Increment generation on start/load and every relevant game mutation; invalidate a pending request when leaving the match. Pausing may defer acceptance without changing state. A stale job must neither consume current RNG nor apply an action.

Important C++ trap: destroying/resetting the last future from `std::async(std::launch::async, ...)` can wait for the worker to finish. Do not perform that destruction synchronously in start/load as the cancellation mechanism. Mark the job stale, retain it until ready, and reap without blocking; bound outstanding jobs rather than launching one per frame. Shutdown may explicitly join. Copy the snapshot on main before launch and measure that copy too.

Minimal deterministic tests: (1) for multiple fixed seeds and fixtures containing Decoy random fallback, tied Agile, Medic/leader targets and pass, compare direct choose with snapshot-worker action fields plus exact rngAfter; verify original state is unchanged before acceptance; then compare complete post-execution Game/save bytes; (2) hold worker completion with a barrier, start/load another game, release worker, assert rejected result and byte-identical replacement state including RNG/progress; repeat for two distinct matches with identical phase/player/RNG to ensure generation is essential; (3) accept one job twice and verify only one application/RNG update; (4) stale future cancellation returns before the blocked worker is released, proving no accidental future-destructor join on the UI path. Tests must use explicit barriers, not sleep-based races. No such worker implementation or tests were added in this review.
